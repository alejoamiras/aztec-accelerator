Blueprint · light tier · draft for approval · 2026-08-18

Aztec 5.2.0 Upgrade

Aztec released version 5.2.0 of its packages today, and the public testnet is already running it. This plan moves the whole project — SDK, playground, and the desktop accelerator's build pins — from 5.0.1 to 5.2.0, lands it as one reviewed pull request, and proves it works against the real network before anything merges. Release notes say the TypeScript surface we use has no breaking changes; the plan verifies that instead of trusting it.

Why the light tier

Of the six risk dimensions, only external coupling scores high (npm publish timing, testnet state, GitHub release assets, a lagging third-party package). Novelty, blast radius, irreversibility, migration cost, and security sensitivity are all low-to-moderate: this is the fourth upgrade cycle, the repo has purpose-built tooling for exactly this, and CI fails closed on the risky parts. One high nominally suggests the mid tier; precedent and tooling make light defensible, and a full codex audit ran anyway — it caught one genuinely blocking problem (phase 2 below), which is the audit system working as intended.

The four phases

Phase 1

Run the upgrade and pin the Windows binary

The repo's own updater script rewrites every version pin and cache marker in one pass. Because 5.2.0 came out today, it trips our 7-day "quarantine" on freshly published packages — per your decision, Aztec's own packages get a permanent, documented exemption (they're the product's first-party upstream; the quarantine stays for everything else). The Windows proving binary gets its checksum recorded by hand with a full paper trail — never automatically, by design.

Proves itself by: the full local test suite (lint, type-checks, ~200 unit tests) green, plus a line-by-line review of the dependency lockfile.

Phase 2 — found by the codex audit

Unblock the test infrastructure's own quarantine

Our CI has a second, separate freshness quarantine: the step that installs the Aztec test network for end-to-end tests. Verified by experiment: it refuses a same-day release, so every e2e test would fail until Aug 25. The fix mirrors your decision in that spot — exempt Aztec's own packages there too (needs a newer npm that supports exemptions), keeping the quarantine for everything else. It touches one CI file and gets validated on this machine before anything is pushed.

Proves itself by: the Aztec test-network installer completing locally under the new settings, plus the CI linter.

Phase 3

Open the pull request, let CI grind

One PR carries everything, staged in clean separate commits. The full CI wall — three test pipelines across macOS, Linux, and Windows, about 20–25 minutes — must go green, including the Windows build that only passes if the hand-pinned checksum is right. The PR stays in draft so nothing can merge before phase 4.

Proves itself by: all four required CI status checks green on the PR.

Phase 4

Prove it on the real testnet, then hand you the merge

Automated checks against the live network: a browser test that deploys an account in both accelerated and fallback modes, the SDK's own end-to-end suite (which asserts the fast native path actually ran, not the silent fallback), and a manual token-transfer run. One known snag may appear here — the shared fee-sponsor contract (see context below). When everything is green, the PR flips to "ready" and the merge is yours.

Proves itself by: live-network tests green including the accelerated path, token flow completing on testnet — or an explicit, logged "blocked, needs owner" state.

Context you need for the decisions

  • The 7-day quarantine. The repo refuses to install any package version published less than 7 days ago — real protection against supply-chain attacks, which have hit npm within minutes of a hijacked publish. Exempting Aztec's own packages is a considered trade: they're the platform this product is built on, versions are pinned exactly, and every upgrade arrives as a human-reviewed PR. The honest cost: for Aztec packages specifically, we lose the one-week observation window.
  • The Windows checksum. Windows builds download a proving binary from Aztec's GitHub release. Its fingerprint is recorded by a person, never a script, so a tampered file can't slip in unnoticed. My recorded fingerprint is honestly a change detector — the real safety comes from you re-computing it independently before merging (one command, included in the code comment).
  • The fee-sponsor contract. The playground pays testnet fees through a shared sponsor contract whose address is derived from its compiled code. Upgrades usually recompile it, moving the address — then someone has to deploy and fund the new one on testnet, which needs your funded Sepolia key. That step is yours alone; the plan stops and asks rather than touching keys.
  • The token library that lags. The playground's token demo uses a third-party package that tracks Aztec releases late — it has no 5.2.0 yet. The plan holds it at 5.0.1 and lets the token-flow tests be the judge of whether that mix works.

Decisions — recorded at approval (2026-08-19)

  1. Token library: held at 5.0.1 per your call ("let's give it a try"); the token-flow tests arbitrate, and its 5.1.0-rc.1 is the first remedy if they fail.
  2. Fee-sponsor contingency: you pointed at a worktree .env — searched every worktree, both clones, and all project env files: the key is not on this machine (only .example templates). If the deploy/fund step is needed, drop the key into packages/playground/scripts/.env (gitignored, verified) and the step runs without the value ever being printed; until then it parks as blocked-on-owner.
  3. Checksum verification: flipped to the agent per your call — verified through two independent channels (downloaded-file hash and GitHub's API-reported digest, required to match), documented in the pinned entry.
  4. CI quarantine exemption: proceeding — it's the same decision you already made for the repo's own quarantine, applied to CI's second, separate one (which provably rejects same-day releases). One reviewed, reversible file edit; veto at PR review reverts to waiting until ~Aug 25.
