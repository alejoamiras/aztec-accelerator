Shipping SDK 5.2.0 to npm

Our published toolkit currently tells the world it works with Aztec 5.0. The code has been on 5.2.0 for a week and has passed every gate we have — it just hasn't been handed to anyone yet. This plan does the handing over: publish the package, point the default download at it, and refresh the playground site in the same motion.

The desktop app is not part of this — it downloads its proving engine at runtime, so an Aztec version change doesn't require a new app. That release is its own separate thing.

Why the lightest tier

Of the six risk dimensions we score, exactly one comes back high: you cannot un-publish. Everything else is familiar ground — this is the fifth time through this machinery, the pipeline is unchanged, no new code ships, and nothing about the package's shape is novel. One high dimension is the textbook case for light: a single reviewer pass rather than a committee.

The "can't undo it" part is handled by ordering rather than ceremony: the package goes out under an opt-in label first, and only a separate second step makes it the default — a step that is a pure label move and can be pointed back at the old version in one command.

The three steps

1

Fix the instructions before they're set in stone

The package's own README travels inside the download, permanently, for whichever version it ships with. Right now it tells people we're on a release-candidate line and that they need a special tag to get current code — both untrue for months. Our internal release handbook has the matching problem, plus it never documents the "make it the default" step at all, which is the exact step this plan relies on.

So: one small pull request correcting three documents, merged before anything is published. It also earns something for free — touching the package re-runs the check that installs our package from scratch the way a stranger would.

Proves itself by: formatting clean, every automated check green, merged.

2

Look before dispatching, then publish

Four things get checked first: nobody has already claimed the 5.2.0 name, no stray label is squatting on it, nothing else is mid-publish, and — unless the pull request just proved it — the packaged file installs and runs in a throwaway folder like a stranger's would.

Then one dispatch does three things: runs the full proving test suite against a locally built copy of the accelerator, publishes the package under the opt-in label with a cryptographic receipt tying it to that exact build, and rebuilds the playground site.

A green run isn't taken as proof on its own. We then read the registry back: the new version is really there, the receipt is attached, the default download hasn't moved yet, and the live site is genuinely serving the new bundle.

Proves itself by: the run finishing green on the exact approved commit, plus all four read-backs confirming reality.

3

Make it the default, then check a stranger's install

A second dispatch moves the default pointer to 5.2.0 — a label change, nothing new published. Then the honest test: in an empty folder, install the package the plain way any newcomer would, and load it. If that fails, the pointer goes straight back to 5.0.1 while we investigate.

Proves itself by: both labels reading 5.2.0, and the plain install-and-load exiting clean.

Things worth knowing

  • Two labels, two audiences. Anyone who wrote "5.0-or-newer" in their project gets 5.2.0 the instant it's published — labels don't hold them back. The default-pointer step only affects people who install without specifying anything. That makes step 2, not step 3, the real moment of exposure — which is why the packaging check happens right before it.
  • Nothing is deletable. Published versions and their tags stay forever. A bad publish is fixed by publishing a newer one, never by removing the old — so mistakes are additive, and the plan never has a step that assumes cleanup is possible.
  • The most likely failure isn't the code. The one real breakage in this pipeline's history was an expired registry credential — the publish signed its receipt, then the upload was refused. If that happens again, everything stops and comes to you; I don't retry and I don't touch credentials.
  • "Failed" doesn't mean "didn't happen." A publish command can fail after the registry already accepted the upload. So on any failure the very first action is reading the registry back and showing you what it says, before anything is classified or retried.
You asked me to run the dispatches autonomously. I've written the authorization as an exact list of four commands — publish, promote, roll back, and redeploy the site — and everything outside that list stops and waits for you, including anything involving credentials or a fix-forward version number.

Open questions

  • Is the publishing credential still valid and narrowly scoped? I can't check this without publishing, and I won't inspect the secret. If you know it's a granular, package-scoped token, say so; if it's an old broad one, this is a good moment to swap it.
  • One known weak spot stays open this cycle. The inner publish workflow can be triggered directly from any branch, skipping the "must be main" guard and the test gate. It's a real exposure if an account is ever compromised. Closing it means editing a publish workflow — and an edited release workflow's first real run is its own first test, which is not something to discover during a release. I've queued it as a follow-up instead. Say the word if you'd rather fix it first.
