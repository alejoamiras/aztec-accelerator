The app forgets where it lives

Move Aztec Accelerator to your Applications folder and “Start on Login” quietly stops working — while Settings keeps insisting it’s on.

What actually goes wrong

When you switch on “Start on Login”, the app asks the operating system to launch a file at one exact location. It writes that location down once and never looks at it again.

1You download the app and run it from Downloads.~/Downloads/Aztec Accelerator.app
2You turn on “Start on Login”. The OS notes down that exact path.
3You drag the app to Applications — the normal thing everyone does. Dragging is a move, so the old location no longer exists.
4Autostart is now dead. The OS is pointed at a file that isn’t there.
5And Settings still shows it ON — because the check underneath only asks “is there an entry?”, never “does it point anywhere real?”

Step 5 is the part that makes this worth fixing properly. A broken feature is bad; a broken feature that reports itself as working is worse, because nobody goes looking for it.

The fix, and the one rule that shapes it

At every launch, the app checks whether the noted-down location still points at something real. If it doesn’t, it quietly rewrites it — editing the existing entry in place rather than deleting and recreating it, because recreating it wipes out the separate crash-recovery setup that shares the same file.

The rule everything hangs on

Only repair when the noted-down location points at nothing. Never when it merely points somewhere different from where you happen to be running from.

That distinction is the whole design. My first draft had it wrong, and both independent reviewers rejected it for the same reason: a leftover copy sitting in Downloads, opened once, would have hijacked a perfectly healthy Applications entry — pointing your login item at a file you’re about to delete. Repairing only dead pointers can’t do that, and it also means two copies racing each other always agree on the answer.

Settings gets honest too. The switch shows what you asked for; a warning line underneath tells you if it isn’t currently working, with a Fix button — or, if you moved the app while it was still running, a note to reopen it from its new home, because that’s the one case the app can’t repair from where it is.

A security bug we found on the way

Shipping today, on Windows

The login entry is written without quotes around it. Because the folder name has a space in it, Windows tries …\AppData\Local\Aztec.exe before the real app — and that folder is one any program running as you can write to. Drop a file there and Windows runs it at every login.

This isn’t a break-out-of-your-account flaw — it needs something already running as you. But it’s ours, and the fix is to quote the path when the entry is first written, not just when it’s repaired.

What five rounds of review actually caught

Three plans were written independently, then checked against each other twice, then audited cold. Nearly every round overturned something the previous one had approved — including things I’d already told you were settled.

Round 1Both reviewers, separately, rejected my “repair whenever it looks different” rule. They were right.
Round 2The safety argument I gave you for skipping the update-window guard was broken by a concrete example I hadn’t considered. The guard went back in.
Round 2I’d rejected a dependency on supply-chain grounds. It was already in the build on every platform — nobody had checked. Reversed.
Round 3A fix I adopted from one reviewer would have broken the Settings toggle whenever an update was downloading. The other reviewer caught the cost neither of us had weighed.
Round 3Nothing anywhere actually launched a repaired entry — so the security fix above was only ever proved against our own model of Windows, not Windows.
Round 4The final reviewer claimed the whole update-window problem was hypothetical. That one was wrong — this repo measured the opposite behaviour last month, and there’s a test on a real Windows machine pinning it.

The decision I need from you

This started as “re-check a path at startup.” It has grown a guard for the window while an update is installing, a new hook inside the Windows installer, changes to the updater itself, and a workflow that builds two full copies of the app to test it. Every one of those traces to a real finding — which is exactly how a plan gets too big to land safely.

Piece 1 — carries the actual fix

The autostart repair itself

Detect and repair dead entries, honest Settings, the Fix button, the Windows quoting fix, and the test layers for all of it. Everything a user would notice.

Piece 2 — correctness

The update-window guard

Stops a repair from firing while the Windows installer has momentarily removed the app. Needs a new installer hook and updater changes.

Piece 3 — proof

The Windows update test rig

The manually-triggered workflow that proves piece 2. Supports it; doesn’t need to be in the same pull request.

My recommendation: ship piece 1 first with the automatic repair switched off on Windows only, then land piece 2 and switch it on. macOS and Linux get the full fix immediately, the Fix button works everywhere, and Windows still gets the security fix — because that one happens when the entry is written, not when it’s repaired. Nothing ships with a known hole.

The alternative is one large pull request with all three. It’s coherent, and every piece is justified — it’s just a lot to land and review at once.

What this still won’t do

  • If you move the app while it’s running, it can’t repair itself until you reopen it from the new location. Settings will say so instead of pretending.
  • On macOS the repair takes effect at your next login — the already-running background job keeps its old path. That’s true today too; this doesn’t make it worse.
  • “Points at a real file” isn’t the same as “will definitely launch”. Desktop environments have their own ways to suppress a startup entry that we don’t model.
  • The rename to AztecAccelerator now has to ship after this, not alongside — it changes the very path the update guard checks against.
