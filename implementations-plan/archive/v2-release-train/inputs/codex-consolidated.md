## BLOCKER

1. **Fully contain the native `bb` worker.** `packages/accelerator/core/src/bb.rs:326-338` buffers all stderr for five minutes before truncating it; `:347-352` reads an unbounded proof file. `src-tauri/src/main.rs:414-429` and `src-tauri/src/updater.rs:558-568` exit/restart without guaranteeing destructor-based child cleanup, so a wedged `bb` can survive the app. Bound stderr while draining, cap/validate proof size, supervise a process group/Windows Job Object, and explicitly cancel/reap before quit/update; add spam, timeout, descendant, and restart-mid-proof tests. **Attacker:** none required—an authentic buggy `bb` suffices. An approved dApp could exploit it only if crafted witness input triggers pathological `bb` behavior; same-user code already has easier kill/OOM routes. **Cost:** 3–5 days.

2. **Close F-10’s consent race.** The 700 ms guard in `frontend-src/bridge.js:15-42,104-109` is optional; only authorization uses it (`authorize.js:107-108`), and promotion becomes actionable on a one-second poll without reliably rearming it (`authorize.js:63-87`). Onboarding, renewal, and update actions omit it. Make guarding default-on and arm from “became actionable,” not initial focus; bind update consent to the displayed update token/version. **Attacker:** a visited malicious webpage, with no local foothold, must time a popup under a normal user click/re-click. It can obtain persistent authorization for itself—not steal another origin’s witness—but that still defeats the advertised MetaMask-style consent boundary. **Cost:** 1–2 days.

3. **Authenticode-sign Windows releases.** `.github/workflows/release-accelerator.yml:204-223` supplies only updater signing; `:927-932` explicitly instructs users to bypass “unknown publisher.” Ed25519 protects existing users’ updates, not first installation. Sign/timestamp the installer and installed executable, decide the `bb.exe` sidecar policy, and gate with `Get-AuthenticodeSignature`. **Attacker:** realistic phishing, mirror, or download-substitution actor; no prior local access. **Cost:** 1–3 engineering days plus certificate/Trusted Signing lead time.

4. **Prove the actual shipped product and v1→v2 migration.** Release smoke launches the packaged app but stops at `/health` (`release-accelerator.yml:392-445`); the native proof E2E uses the Linux headless server, not an installed desktop/browser/TLS path. macOS/Windows tests explicitly omit real trust installation (`tests/trust_macos.rs:1-9`, `trust_windows.rs:1-9`). Cut a new signed RC—the current RC lacks recent audit fixes—and gate a packed SDK → browser → installed desktop → native proof, plus a stateful 1.0.7 profile upgrade preserving origins, config, autostart, and HTTPS across all OSes. `core/src/config.rs:38-53` currently ignores the old `safari_support` field and `config_version`. **Attacker:** none; this covers packaging and migration regressions. **Cost:** 4–7 days plus RC soak.

5. **Make uninstall actually uninstall.** Windows’s hook removes CA files only (`src-tauri/nsis/hooks.nsi:101-160`), not Run/StartupApproved state or the repeating recovery task; cleanup exists elsewhere in `autostart.rs:1968-1978` and `crash_recovery.rs:461-491`. macOS/Linux deletion can leave LaunchAgent, `.desktop`, systemd, and browser-trust state. Add an idempotent `--prepare-uninstall`, invoke it from NSIS, and provide explicit cleanup flows for DMG/AppImage/deb. **Attacker:** none. The residual CA is keyless and loopback-constrained, so this is lifecycle hygiene, not an escalated security claim. **Cost:** 3–5 days.

6. **Separate stable publication from fleet promotion and rehearse recovery.** The stable-release job creates the release and immediately overwrites production `latest.json` (`release-accelerator.yml:876-998`); verification follows afterward. `docs/RELEASE_RUNBOOK.md:87-110` recommends deleting tags/releases and manually restoring a feed. Installed bad version N cannot auto-downgrade, and crash-on-start N cannot self-update. Publish artifacts first, explicitly promote after acceptance/soak, add a least-privilege freeze/fix-forward workflow, and drill N+1 recovery. **Attacker:** none—a validly signed bad build is enough; signing does not protect against mistakes. **Cost:** 2–4 days.

7. **Fix the SDK release contract.** The checked-in package is `0.0.0`, exports source (`packages/sdk/package.json:3,11`), and CI rewrites version/exports immediately before publishing (`_publish-sdk.yml:79-123`). Versioning follows Aztec, so fixes become `X.Y.Z-revision.N`, which normal `^X.Y.Z` consumers will not receive. No `npm pack` artifact is installed and tested. Define independent desktop/wire/Aztec/SDK version axes, test the exact tarball in fresh Node/Vite/typecheck consumers, and attach `MIGRATION.md` to a named release. Desktop v2 may coexist with SDK 5.x, but that must be explicit. **Attacker:** none; this is artifact and compatibility failure. **Cost:** 2–4 days.

## SHOULD-FIX

- **F-07 and proving fairness:** unauthenticated drive-by suborigins can fill the consent queue; an approved origin can retain roughly `8 × 50 MiB` and start parallel downloads before the single proof permit (`authorization.rs:206-218`; `server/prove.rs:188-246,271-345`). Add deny cooldown, per-origin fairness, aggregate-byte budgeting, and download singleflight. **Cost:** 2–3 days.

- **F-09 replay:** an actor controlling the production feed—but not the signing key—can replay a withdrawn, still-valid higher release because signed `pub_date` has no freshness state. This is a realistic narrow infrastructure actor, not drive-by or local code. Add recoverable highest-seen/date state or expiring metadata. **Cost:** 1–2 days; TUF-like design is weeks.

- **Define SDK errors:** 403/503/network/bad bodies fall back, while other `ky` `HTTPError`s escape (`accelerator-prover.ts:399-535`), despite stable server codes in `core/src/server.rs:495-565`. Publish typed fallback/retry/fatal contracts. **Cost:** 2–4 days.

- **Support diagnostics:** rotating owner-only logs are good (`src-tauri/src/main.rs:545-570`), but “Show Logs” is development-only (`tray.rs:91-112`), Windows paths are undocumented, and `panic = "abort"` has no persisted crash record. Add production log access and a privacy-reviewed diagnostic bundle without witnesses. **Cost:** 3–5 days.

- **Release provenance:** Apple/updater secrets reach every build leg (`release-accelerator.yml:204-215`), and tags identify the unpatched source SHA rather than the shipped version (`:164-187,607-650`; the 1.0.7 tag contains `1.0.7-rc.1`). Scope secrets and bind version, SHA, and artifacts with provenance. **Cost:** 2–5 days.

- **Packaging gaps:** install/remove-test the `.deb`, publish signed checksums/attestations, and validate/notarize the final DMG container—not only the mounted app. **Cost:** 1–2 days.

## NICE-TO-HAVE

- Signed runtime `bb` revocation policy and OS sandboxing. There is no demonstrated vulnerable `bb`; same-user attackers already read the witness workspace. **Cost:** days to weeks.
- Opt-in crash telemetry, daily cryptographic feed verification, and documentation cleanup. Several runbook test counts/assets and Linux updater status are stale. **Cost:** hours to one week.

The security and update foundations are substantially better than average: private workspaces, bounded request bodies, serialized proving, verified/leased downloads, signed manifest binding, three-OS updater smokes, real Linux trust-chain testing, and signed/notarized/stapled macOS apps are all solid. It is close to a serious release candidate, but not production-ready v2. The single biggest risk is a validly signed but bad major update being promoted fleet-wide before the installed desktop’s real proving and state migration have been exercised, with no automatic rollback once users receive it.
