Autostart arc · piece 2 of 3 · blueprint mid, rev 3

A do-not-disturb sign for the seconds an update is installing

Piece 1 taught the app to repair its own "Start on Login" entry — everywhere except Windows, where the repair stayed switched off. This piece is the reason it can now be switched on.

The problem, in one scene

On Windows, applying an update means the app hands control to an installer and exits. For a few seconds, the installer has deleted the old program and not yet finished writing the new one. If any copy of the app wakes up in exactly that window and runs its repair, it "fixes" the login entry to point at whatever transient copy it happens to be — and after the installer finishes and that copy is deleted, autostart is broken again. The very bug this whole arc exists to fix, reintroduced by its own cure.

The old safety net can't help: the file-lock the updater holds dies with the exiting process, which is precisely when the danger starts.

The fix: a marker file with a receipt

1Before handing off to the installer, the updater writes a small marker file: a one-time ticket number, which version is being installed, where it will land, and a hard expiry (~15 minutes).
2While that marker exists: no repair, no crash-recovery re-arming, no new update, no turning autostart ON. Turning it OFF always still works.
3The installer itself, as its last act after every file is in place, stamps the receipt — it hands the ticket number back. New installer code; a release can't fix its own installer, so it ships right the first time.
4The freshly installed app, at next launch, removes the marker only when everything matches: right ticket, right version, right location, and crash recovery put back the way the user's settings say. Then normal life — including the Windows repair, enabled at last — resumes.
5If anything went wrong and no one can ever match the ticket, the marker simply expires and the app carries on. The sign can never get stuck on the door.

What review added this round

Three audit passes (two in parallel, one fresh-context) rejected early revisions and were folded:

  • Every check now happens while holding the lock, right before acting. Both auditors independently showed that a check made before taking the lock recreates the original bug through a side door — twice, at two different sites.
  • Failure paths are direction-aware. If an install fails and the user wants autostart ON, remove the marker first, then re-arm; if OFF, confirm the disarm first, then remove. The wrong order can leave the app silently re-launching against the user's wishes — permanently.
  • A planned test would have deleted a real setting on a developer's machine. Caught at plan time — the same class of mistake piece 1 caught only after CI ran. The test now uses injected counters instead of the real scheduler.
One design point reopened, openly

The original ledger asked the installer to defend its receipt-file against a filesystem trick (junction redirection). The installer language has no primitive for that, building one would be heavy machinery against an attacker who — running as the same user — could simply write the receipt directly. The requirement is amended with a written rationale, in both ledgers, rather than quietly skipped. The receipt can't be forged into acceptance either way: the ticket number, version and path still have to match.

What lands in this PR

  • The marker module with an exhaustive state-table test (every stranded state has a defined exit).
  • The installer receipt hook + a wine-based harness case that fails if the hook never fires — a misspelled hook name is silently ignored by the installer templates, so the test must prove the positive.
  • The updater and the repair/rearm/toggle paths made marker-aware — four call sites, each checked under the lock.
  • The Windows repair switched on, and the CI smoke flipped to prove it: a deliberately broken login entry must come out healed to the exactly-quoted installed path — plus a new scenario proving a live marker suppresses everything it should.
