# Lessons — cohort B3 (bb worker containment)

## Stage 1: capped stderr drain (F4) + proof validation (F5) + injectable timeout

- **F4**: `prove()` used `wait_with_output()`, which buffers ALL of bb's stderr into memory for up to
  PROVE_TIMEOUT. Replaced with `drain_capped(reader, cap)` — retains ≤64KiB but drains to EOF (so bb
  never blocks on a full pipe) and counts the total — run via `tokio::join!(drain, child.wait())` under
  the timeout. Cap-and-continue, NOT fail-closed (stderr volume is a diagnostic, not an integrity
  signal; aborting a valid proof over chatty bb would be self-inflicted DoS).
- **F5**: exit-code success was the ONLY gate, so an empty proof → a 4-byte header-only "success" and a
  non-32-aligned file was silently floor-divided. Added `validate_proof_len(len)` (pure): reject empty,
  >64MiB (checked on the on-disk size BEFORE the otherwise-unbounded `std::fs::read`), and
  non-32-byte-aligned. All three checks are length-only, so the pure fn is fully unit-testable.
- **Injectable timeout**: `prove()` → thin wrapper over `prove_with_timeout(..., timeout)`
  (bind_with_retry_inner pattern) so the timeout/kill path is testable in 150ms, not 5 min.
- **Testability**: `drain_capped` and `validate_proof_len` are pure/standalone → unit-tested directly.
  `&[u8]` DOES impl `tokio::io::AsyncRead`, so drain_capped tests need no mock reader. A fake-bb harness
  (`install_fake_bb` writes a `/bin/sh` script at BB_BINARY_PATH, `EnvGuard` clears on drop, `#[serial]`)
  drives `prove()` end-to-end (empty/misaligned/chatty-stderr/hang) — Unix-only (shell script), which
  the prove path is anyway.
- **Mutation proofs**: drain cap (`room.min(n)` → `n` → retained 8192≠64 fails); validate empty-check
  (neutered → both the unit AND the e2e fake-bb test fail). The redundant OUTER guard `if retained.len()
  < cap` is NOT the cap — `room.min(n)` is; mutating the outer guard alone doesn't break anything
  (lesson: mutate the load-bearing expression, not a redundant optimization around it).
- 244 core tests green; fmt + clippy clean. (Env note: `export PATH=$HOME/.cargo/bin:$PATH`;
  `bun run --cwd packages/accelerator prebuild` for the bb sidecar; carried from B2 lessons.)

## Stage 2: child-tree containment (F6)

- **Mechanism (uniform API, per-OS impl)**: `containment::{configure, Guard, terminate_inflight}`.
  - Unix: `cmd.process_group(0)` makes bb its own group leader (pgid==pid); a `static Mutex<Option<i32>>`
    registry + RAII `Guard` (Drop SIGKILLs the GROUP iff still registered → covers client-disconnect
    future-drop / timeout / panic, incl. grandchildren `kill_on_drop` misses); `terminate_inflight()`
    `kill(-pgid, SIGKILL)`. `libc` added (Unix-only dep) for killpg.
  - Windows: a process-lifetime Job Object with `KILL_ON_JOB_CLOSE` (static `OnceLock<isize>`, never
    closed); each bb `AssignProcessToJobObject` + `IsProcessInJob` verify, FAIL-CLOSED (prove errors if
    unassigned — codex); the OS reaps the tree when the process exits (any exit, incl. the updater's
    NSIS-handoff `process::exit`). Added the `Win32_System_JobObjects` windows-sys feature.
  - Linux PDEATHSIG CUT (final-pass trim); macOS crash-orphan is a documented residual.
- **Exit-site wiring (single choke point)**: `RunEvent::ExitRequested` else-branch (exit ALLOWED) calls
  `bb::terminate_inflight()` — covers BOTH tray-quit (`app.exit(0)`) and updater `app.restart()` since
  both fire that event. Plus an explicit pre-`install()` call in `updater.rs` (Windows install() →
  process::exit bypasses the Tauri event loop, so bb must die before the NSIS handoff touches files).
- **Testability**: the decisive F6 test spawns a fake-bb that forks a `sleep 300` GRANDCHILD; running
  prove() concurrently, then `terminate_inflight()`, must kill the grandchild (`kill(gpid,0)==ESRCH`).
  Mutation: removing `process_group(0)` leaves the grandchild in the test's group → survives → FAILS.
  **Gotcha**: the first version HUNG under the mutation (prove_task blocks forever on a live bb, so the
  runtime shutdown waits on it). Fixed by `prove_task.abort()` + a best-effort grandchild-SIGKILL before
  the assert → the mutation now FAILS cleanly in ~2s and doesn't leak the grandchild. (Also cleaned a
  leaked `sleep 300` from an earlier mutation run — kill only my own by pattern.)
- **Windows verified locally WITHOUT CI**: `rustup target add x86_64-pc-windows-gnu` +
  `cargo check --target x86_64-pc-windows-gnu` compiled the entire cfg(windows) Job Object path (all
  windows-sys API names/structs/consts correct) — caught an unused import and saved a ~24-min CI
  round-trip. **Do this for every cfg(windows) change before pushing.**

## Stage 3: panic hook + Show Logs in production (observability fold-ins)

- **Panic hook** (main.rs, after tracing init): persists panics to `log_dir()/panic.log`
  SYNCHRONOUSLY (create+append+flush) — the tray app has no console, `panic = "abort"` (release) means
  no unwind, and the tracing file layer is `non_blocking` (its worker may not flush before abort). The
  hook chains the previous (stderr backtrace) hook. Write logic extracted to `write_panic_record(path,
  location, payload)` so it's unit-testable (the hook install ends in abort, untestable); the test
  asserts append-not-overwrite + location + payload. Note: main.rs tests are BIN tests — run via
  `cargo test --bin AztecAccelerator`, NOT `--lib`.
- **Show Logs in prod** (tray.rs): the item is now built once and included in BOTH the dev and
  production menus (the handler `open_in_browser(&log_dir())` was never dev-gated) — the only in-app
  path to a released build's logs. Menu-construction isn't unit-tested (needs a Tauri app); covered by
  the wdio smoke (a broken menu fails tray build → app won't start).
- README: added the Windows log path (`%LOCALAPPDATA%\aztec-accelerator\logs\`) + a panic.log note, and
  corrected the stale "Show Logs is dev-only" line.

## Codex review round 1 (6 findings: 3 High) — all fixed

- **H1 Windows Guard had no Drop** → cancel/timeout left grandchildren in the still-open job until app
  exit. FIX: `Guard { armed }` with a Drop that `TerminateJobObject`s on abnormal drop; `finish()`
  disarms (mirrors the Unix guard).
- **H2 pre-install terminate unconfirmed** (fire-and-forget + async kill) violated the ratified
  "unconfirmed reap ⇒ abort update". FIX: `terminate_and_confirm(timeout) -> Result` (Unix: SIGKILL then
  poll `kill(-pgid,0)==ESRCH`; Windows: TerminateJobObject then poll `QueryInformationJobObject`
  ActiveProcesses==0); `perform_update` now aborts the install on Err. Placed AFTER the download and
  BEFORE the marker transaction so an abort is a clean `return` (no marker/recovery unwind). `kill`
  fire-and-forget stays as `terminate_inflight` for the quit path (never block quit).
- **H3 SetInformationJobObject return discarded** → job could exist WITHOUT KILL_ON_JOB_CLOSE while
  assignment succeeded (containment silently off). FIX: check it; on failure CloseHandle + cache 0 →
  register() fails (fail-closed).
- **M4 pgid-stale window** could extend to the timeout if a grandchild held stderr open (join! waits for
  drain). FIX: drain in a SPAWNED task (keeps pipe empty) and `finish()` the guard the instant
  `child.wait()` returns — decoupled from drain; collect drain bounded (2s) + abort so it can't hang.
- **M5 F5 metadata-then-read TOCTOU**. FIX: `read_capped` = one open + `take(MAX+1)` + read; validate the
  actual bytes.
- **L6 flush ≠ durable**. FIX: `sync_all` (fsync) in write_panic_record.
- Windows-verified locally: `cargo check --target x86_64-pc-windows-gnu` compiled the whole rewritten
  Job Object path (QueryInformationJobObject, JOBOBJECT_BASIC_ACCOUNTING_INFORMATION, the Guard Drop)
  clean. 245 core + 115 src-tauri green; fmt+clippy clean.

## Codex review round 2 (H1/H3/M5/L6 verified; H2 + M4 still open) — all fixed

Round 1's `terminate_and_confirm` killed the *current* bb but did not stop a *new* one starting before
install, and finishing the guard the instant bb exited could orphan grandchildren. Both are the same
lesson as B2's HIGH: an invariant ("no bb runs during install") stated in prose that nothing enforced.

- **H2a — confirm didn't prevent a NEW prove.** A prove starting in the window between confirm and
  install would run during NSIS (a live `bb.exe` blocks the installer from replacing it). FIX: a **quiesce
  latch**. `begin_quiesce()` returns an RAII guard held across confirm+install; while set, `Guard::register`
  FAILS. Unix: `quiescing` lives in the SAME mutex the terminator takes the pgid under, so once the latch is
  set no register can slip in after the terminator confirmed the registry empty. Windows: an atomic checked
  before AND *after* `AssignProcessToJobObject` (kill+err on a raced assignment); the poll in
  `terminate_and_confirm` is the fail-SAFE backstop (a bb that races in keeps ActiveProcesses>0 → the update
  ABORTS rather than installing over it). Guard drop (aborted install) re-opens proving. Mutation-proved:
  `register_is_refused_while_quiescing_then_reopens`.
- **H2b — confirm was fail-OPEN.** Unix treated EVERY `kill(-pgid,0) == -1` as "gone" (EPERM would falsely
  confirm); Windows mapped a *failed* `QueryInformationJobObject` to 0 active. FIX: Unix confirms only on
  `errno == ESRCH`; `active_processes` returns `Option<u32>` and `None` (query failed) is NOT a
  confirmation. Both then time out → Err → abort install (fail-closed).
- **M4a — finish() immediately unregistered while grandchildren might remain**, making them unkillable once
  the registry is cleared. FIX: `finish()` SIGKILLs the group FIRST (reaping any orphan) THEN clears — and
  that kill is also what makes the bounded stderr drain EOF promptly. Mutation-proved:
  `finish_reaps_a_straggler_grandchild_on_the_success_path`. Residual (documented): the reap uses a GROUP
  kill under the lock microseconds after `child.wait()`, so a pid-recycle-into-new-group-leader in that
  window is physically impossible — not worth WNOWAIT's complexity.
- **M4b — early returns detached the spawned drain task.** FIX: `AbortingDrain(JoinHandle)` aborts on drop,
  so timeout/wait-error paths tear it down.

Verified: 26 bb + 223 other core + 115 src-tauri green; fmt+clippy clean; Windows path
`cargo check --target x86_64-pc-windows-gnu` clean. Both new tests mutation-proved (neuter the guard →
red).

## Codex review round 3 (H2b/M4a/quiesce-lifetime verified; H2a + M4b reworked)

Round 2's latch gated *registration*, but bb is SPAWNED before it registers — so a prove already past
spawn (with a grandchild `kill_on_drop` can't reach) could run during install. The latch could not see it.
Same failure family again: the guarded thing (register) wasn't the thing that needed guarding (spawn).

- **H2a — FIX: fold spawn+register into one `containment::spawn_and_register(cmd)` under the lock.** The
  quiescing check, `spawn`, and pgid/job registration are now one synchronous critical section (no `.await`
  under the lock). `begin_quiesce` takes the SAME lock, so it either wins the race (spawn refused) or waits
  out an in-flight spawn (bb ends up registered/in-the-job → the terminator kills it / the confirm poll
  sees it and aborts the install). Windows swapped its r2 atomic for a `Mutex<bool> GATE` held across
  spawn+assign — the atomic's check/assign could never be made atomic without a lock. Mutation-proved:
  `spawn_is_refused_while_quiescing_then_reopens`.
- **M4b — FIX: shared `DrainAcc` (`Arc<Mutex<(Vec,u64)>>`).** `drain_capped_into` writes retained+total
  incrementally, so a 2s-timeout/abort recovers the PARTIAL stderr instead of returning empty. (In practice
  the M4a group-kill EOFs the drain first; this is the pathological-reader backstop.) `drain_capped` kept as
  a `#[cfg(test)]` wrapper so the unit tests are unchanged.

Verdict trajectory: r1 6 findings → r2 (H2a/H2b/M4a/M4b open) → r3 (H2a/M4b open) → r4 pending. Verified:
26 bb + 223 core + 115 src-tauri green; fmt+clippy clean; Windows cargo-check clean; H2a mutation-proved.

## Codex review round 4 (deadlock/fork/M4b/success-atomicity verified; one Windows failure-path Medium)

r4 cleared the scary ones: **no deadlock** holding the containment mutex across `tokio::Command::spawn`
(tokio's reaper never calls user drop code under its registration lock; our mutex is never held across
`.await`; single-thread runtime can't have another task holding it while yielding), the **fork/exec**
copied-locked-mutex is never touched by the child before exec, and **M4b**'s accumulator is
snapshot-safe. Success-path spawn/contain atomicity is airtight on both OSes.

- **Remaining Medium (Windows failure path).** If `AssignProcessToJobObject` (or the `IsProcessInJob`
  verify) FAILS, returning Err dropped `child` while holding `GATE`, but `kill_on_drop` only *initiates*
  async termination — a waiting `begin_quiesce` could confirm the job empty and install while the
  uncontained bb.exe was still dying / had forked an uncontained descendant. FIX: `contain_spawn_failure`
  runs BEFORE releasing `GATE` on every post-spawn failure — `TerminateJobObject` (reaps the
  assign-succeeded-verify-failed case) + `TerminateProcess`+`WaitForSingleObject` on the direct handle
  (kills+WAITS even when assignment never took). Needs `Win32_System_Threading` (already enabled).
  codex's "fully airtight" alternative — CREATE_SUSPENDED then assign then ResumeThread — was rejected as
  over-plumbing for a rare OS-error path (needs the primary-thread handle via a thread snapshot).

Lockfile: `accelerator-core`'s round-1 `libc` edge finally propagated into `src-tauri/Cargo.lock`.

Verdict trajectory: r1 6 → r2 4 → r3 2 → r4 1 (Windows failure path) → r5 pending. 26 bb + 115 src-tauri
green; Windows cargo-check clean; fmt+clippy clean.

## Codex review round 5 (handle/wait/suspended-rejection/holistic verified; one fail-open Medium)

r5 cleared handle-lifetime (non-consuming waits), the 5s blocking wait (rare, finite, stalls not
deadlocks), the CREATE_SUSPENDED rejection (µs descendant residual ledgered, NOT release-blocking), and
the HOLISTIC B3 pass (F4/F5/F6/quiesce/confirmed-terminate/panic/Show-Logs coherent, no AbortingDrain
regression).

- **Remaining Medium — same fail-open class as H2b.** `contain_spawn_failure` ran the right calls but
  IGNORED `WaitForSingleObject`'s result: `WAIT_TIMEOUT`/`WAIT_FAILED` (or a failed `TerminateProcess`,
  which then times out the wait) would release `GATE` with the direct child UN-confirmed. FIX: it now
  returns `true` ONLY on `WAIT_OBJECT_0`; a `false` (or the no-raw-handle path) sets a process-lifetime
  `POISONED` flag that makes `terminate_and_confirm` return Err — so updates ABORT rather than install over
  a possibly-live uncontained bb, until the app restarts (fresh job clears it). Fail-closed.
- **Load-bearing test added** (`contain_spawn_failure_confirms_the_direct_child_is_dead`, `#[cfg(windows)]`,
  Windows CI): drives the helper against a real `ping` child and asserts a CONFIRMED exit — the wait
  semantics cargo-check can't see. Compiles for x86_64-pc-windows-gnu; runs per-OS in CI (can't run on the
  Linux dev box).

Verdict trajectory: r1 6 → r2 4 → r3 2 → r4 1 → r5 1 (fail-open confirm) → r6 pending. 249 core + 26 bb +
