# B7 — SDK release contract: lessons

## The load-bearing bug the recon agent surfaced: a DEAD READ in production

The SDK's 403 handler read the server error code from `err.data` as an OBJECT — but the accelerator sends
its error body as `text/plain` carrying a JSON string (pinned by the Rust test
`prove_error_responses_stay_text_plain`), so `ky` sets `err.data` to a STRING. `typeof err.data ===
"object"` was therefore FALSE in production → the code was never read (logged as `undefined`). The test
used `Response.json(...)` (application/json → object), the OPPOSITE branch from prod, and asserted only the
`denied` phase — so the mismatch was invisible. F14's `parseServerError` `JSON.parse`s the string form (and
still accepts an object), and the new fixtures use text/plain to hit prod's exact path.

**Lesson: when a test constructs the wire differently from production (content-type, encoding), it can pass
while the prod branch is dead. Pin the REAL wire shape.** (Same family as the recurring "invariant asserted
in prose the type system doesn't enforce" from B3/B5.)

## F14 taxonomy (rev 3)

The accelerator is an OPTIMISATION, so the bias is: degrade to WASM for everything RECOGNISED, and throw the
typed `AcceleratorHttpError` only for a caller MISCONFIGURATION or a genuinely unexpected response —
otherwise a real integration bug hides behind "slow but working". Precisely (matches `#fallbackOrThrowHttp`):
the degrade set is matched BY STATUS — **every** `403` (denial / `version_not_allowed` / `authorization_
cooldown`) and **every** `408`/`413`/`429`/`503`, plus `500 download_failed`/`prove_failed` — so an unknown
`403`/`503` *code* still degrades. THROW is only `400`, a `500` with an unrecognised code, or an unexpected
status. `version_not_allowed` gets its own `version-mismatch` phase; `authorization_cooldown` (B2 F9)
degrades WITHOUT a fresh `denied` phase. Applied at both the primary and the HTTP-retry catch so a misconfig
surfaced only on retry isn't masked either.

**Round-2 self-error (codex caught):** my first doc pass wrote "any unrecognised status/code throws", which
contradicts the by-status degrade above (an unknown 403/503 code degrades, not throws). A token-presence
doc-sync test can't catch that kind of SEMANTIC drift — only reading the docs against the classifier does.

## F13 verdict: KEEP DEPS (and a corrected npm mechanic)

Predeclared (D-C13/D-C29): default `npm install` is decisive; the exact-host must be a singleton @aztec
graph. Verdict KEEP DEPS holds — but the REASON I first wrote was factually wrong, and codex caught it.

**Wrong (round-1):** "peers just nest a duplicate like a dep, so they buy nothing." **Right (empirically
verified — `evidence/f13-peer-vs-deps.sh`, npm 10 default resolver):** on a version-skewed host a DEP
install SUCCEEDS (the dependent nests its own correct copy) while a PEER install FAILS with **ERESOLVE** on
the DEFAULT resolver — a direct/root peer conflict has no valid at-or-above placement (npm RFC 25). The real
tarball confirms both ends: exact-host → all @aztec/stdlib deduped to ONE (singleton gate); conflict-host →
install succeeds with the SDK's 5.0.1 nested (10 locations) beside root's 5.0.0.

Round-3 caught me OVERCORRECTING: I then called peers "strictly worse", which is also an overclaim. The
honest trade-off — peers turn a version skew into an immediate `npm install` ERESOLVE (fail-fast, but blocks
install on ANY skew), whereas deps install and DEFER a cross-version incompatibility to runtime. KEEP DEPS
is an owner choice prioritising installability + graceful degradation, explicitly accepting that runtime-skew
risk — not a free win.

**Round-4 self-error (codex caught):** I first scoped that runtime risk to "the WASM path (accelerator path
is handshake-protected)" — WRONG. The SDK↔accelerator `/health`/`x-aztec-version` handshake advertises the
SDK's OWN pinned version vs the accelerator's bb cache; it gates SDK↔accelerator, never sees the host dApp's
version, so it can't catch a host↔SDK skew. A modern multi-version accelerator just downloads the SDK's
version and proves — so the skew risk applies to BOTH native and WASM proving. Lesson: don't assert a
protection boundary without tracing WHICH two versions the handshake actually compares.

**Lesson: don't enshrine a resolver/tooling mechanic in a committed decision artifact on reasoning alone —
run the 30-line experiment (a tiny is-number repro disproved my first npm claim in seconds). And when a
review corrects an overclaim, don't overcorrect into the opposite one — record the actual trade-off.**

## Publish hardening

- `prepare-sdk-publish.ts` — the exports rewrite is now a committed, unit-tested pure function (was an
  inline `node -e`), shared by the publish workflow and reproducible in CI.
- `tarball-consumer` job — the ONLY thing validating the PUBLISHED artifact; the playground consumes the
  SDK via `workspace:*` (source exports), so a broken dist rewrite / missing dist would ship undetected.
- The heavy `@aztec/*` install makes the job CI-only (like the B5 Windows harness) — the shell logic is
  shellcheck-clean and the pure rewrite is unit-tested locally. Verified end-to-end locally once (real
  tarball, real @aztec graph) before pushing, to avoid burning a 10-min CI cycle on the newest job.

## A public-union addition is a cross-package break

Adding `"version-mismatch"` to the SDK's exported `AcceleratorPhase` compiled fine in the SDK and passed all
SDK checks — then broke the PLAYGROUND. The playground's `AnimationPhase = AcceleratorPhase | ...` and it
consumes the SDK via `workspace:*`, so its exhaustive-return `getFrameFn` switch lost a return path (TS2366)
the moment the union grew. The SDK-scoped gates were blind to it; only the full repo `bun run test`
(which typechecks every workspace) surfaced it.

**Lesson: widening a published union/enum is an API change for every `workspace:*` consumer that matches it
exhaustively. Run the FULL `bun run test`, not just the changed package's — the standing pre-push rule
earned its keep here.** (Same shape as the recurring cross-package invariant lessons; here the type system
DID enforce it, but only at the consumer, only under a full-repo typecheck.)
