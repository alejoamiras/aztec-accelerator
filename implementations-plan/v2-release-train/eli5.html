Blueprint · deep tier · autonomous

Shipping Aztec Accelerator v2.0

What the release train fixes, why each piece matters, and how the plan was pressure-tested before a single line of code — in plain terms.

The accelerator is a strong release candidate today, but not yet a production 2.0. Six things stand between here and there. This plan fixes all six, proves each fix, ships the desktop app as 2.0.0 on macOS, Linux and Windows, publishes the matching SDK — and does it end-to-end without needing you at the keyboard.

One thing is deliberately not here: Windows code-signing (B1). It has the longest lead time of anything in the report and you chose to start that clock separately. Everything else is in scope.

01 The six blockers, in plain language

B2 · consent · security

Close the click-steal race

The "Allow this site?" popup has a 700ms guard so a malicious page can't time a click and self-approve. Today that guard is only on one popup and arms at the wrong moment. We make it default-on everywhere and arm it when the button truly becomes clickable.

The only blocker a remote web page with zero local access can exploit.

B3 · the prover

Fully contain the bb worker

The native prover can spew unbounded error text into memory, hand back a truncated proof as if it succeeded, and — worst — keep running after the app quits or updates. We cap it, validate its output, and guarantee it dies with the app.

No attacker needed; a buggy prover is enough.

B5 · lifecycle

Make uninstall actually uninstall

Removing the app leaves behind autostart entries, a recovery task that relaunches it, and trust state. We add a real cleanup step the uninstaller runs — and it only removes what this install owns.

Hygiene, not an exploit — but it's what "production" means.

B7 · the SDK

Fix the SDK's release contract

The published package is never tested as it actually ships, some errors escape untyped, and the migration guide isn't even in the download. We test the real tarball in fresh projects and give errors a proper type.

Breaks integrations silently, not maliciously.

B6 · release engineering

Separate "publish" from "go live"

Today one job both publishes a build and points every user's auto-updater at it, with no way back. We split them: publish and verify first, flip the switch only after every gate passes, and keep a real rollback lever.

A validly-signed bad build is all it takes to hurt the fleet.

B4 · the proof · goes last

Prove the shipped product upgrades

Nothing today tests the installed app doing a real proof over HTTPS, or a 1.0.7 user upgrading to 2.0 without losing their settings. We build that test on all three OSes — it's the gate the real release must pass through.

Catches packaging & migration regressions nothing else would.

02 Why you can trust the plan before any code

This plan wasn't written once and shipped. It was drafted three independent ways, then attacked in four escalating rounds. Each round found real defects — including several in my own consolidation — and every one was folded in and recorded in the decision ledger.

The pattern worth knowing: three separate times I wrote a security rule as a comment that the code didn't actually enforce ("this can't happen") — and each time an auditor showed a one-line bypass. Rev 4 has a standing rule now: every "cannot happen" invariant is enforced by the type system with a proof, never by convention. That's the difference between a plan that sounds safe and one that is.

03 How it ships

Six cohorts, merged one at a time onto a green main, in this order:

  1. B2 → B3 → B5 → B7 → B6 — each its own branch and PR stack, every security fix mutation-proved (revert the fix, watch the named test fail, restore).
  2. B4 last — because its 3-OS installed-product test is the gate the real release runs through.
  3. Cut 2.0.0-rc.N — published, run through the full gate suite, soaked ≥2h.
  4. Stable as a private draft — gated on the exact bytes that will ship; published only once it passes, so a failed build was never public.
  5. Promote — flip the updater feed to 2.0.0, then publish the SDK's next revision and verify a clean install from npm.

If anything can't be done safely inside the granted authorization — a bad build that's already public and would need a 2.0.1, or a trust-seeding step that can't be automated on an OS — the run stops and surfaces to you rather than improvising. Those exit points are named in the ledger.
