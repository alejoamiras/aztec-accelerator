Bun 1.4 Migration

Bun 1.4 is a big release, and this repo runs on Bun for everything — installs, scripts, tests, publishing. The plan moves us there in guarded stages, adopts the new bun-native capabilities exactly where they pay for themselves, and refuses the rest. One hard fact shapes everything: Bun 1.4.0 currently crashes a core piece of the Aztec libraries' logging (we reproduced it, found a clean bypass, and will hand the Bun team a bug report). A second, untestable-until-we-try risk decides whether the version flip lands now or waits for Bun's fix.

Why the mid tier

Blast radius is high (the toolchain under every build and test, 23 pinned version sites, the publish pipeline) and there's real external coupling (an upstream Bun bug, Aztec's internal logger behavior). Novelty and irreversibility are low — everything is phased and revertable. Two highs → mid: the plan got three independent adversarial reviews (a parallel codex + Claude audit on the draft, then a fresh-context codex re-audit of the consolidated result). Sixteen material findings were folded in across two revisions, including two the plan itself had gotten factually wrong.

The five phases

Phase 1 — works on today's Bun

Stop the bleeding, centralize, prepare

The SDK publish pipeline currently floats to "whatever Bun is newest" — it gets pinned first. Then the 23 scattered version pins collapse into one .bun-version file (guard-tested so nobody reintroduces an inline pin). The crash bypass goes in (one line in three test-setup files, using a switch Aztec's own logger provides — with a tripwire test that fires if Aztec ever removes that switch). Finally, Bun's new "isolated" install layout — with a measured before/after and an explicit exit rule: if it costs more than a small fix or the benefit is immaterial, it gets cut rather than dragging the urgent pin fix down.

Proves itself by: full test suite + CI green on today's Bun, an empty lockfile diff, and a resolution probe on the one release script the new layout could genuinely break.

Phase 2 — the evidence spike

Answer the unknowns with the real 1.4 binary

Clean install and full suite under 1.4. Then the decisive question: a second worker-based code path (inside the proving library, only reachable in live end-to-end runs) either works under 1.4 — or crashes the same way the logger did. Green means the migration proceeds; a crash (with the exact fingerprint, from that specific run) means we park the version flip until Bun ships a fix, and everything from Phase 1 still lands. Also verified here: the stricter TLS rules against our local HTTPS setup, and how the new parallel test modes interact with our test bootstrap. The Bun bug report gets drafted for you to file.

Proves itself by: every question having a recorded answer with output quoted — a "no-go" answer passes this phase too; what it blocks is the next one.

Phase 3 — the flip (only on a green spike)

Version bump and nothing else

One line: .bun-version → 1.4.0, plus one isolated lockfile refresh commit. Deliberately boring so that if anything regresses later, this commit is trivially bisectable and revertable. (One follow-up waits on our own supply-chain rule: the Bun types package is itself younger than our 7-day quarantine — it gets bumped only once it ages out. No exemptions, even for our own migration.)

Proves itself by: full CI green with every job now running 1.4.

Phase 4 — tooling adoptions (after the flip is green)

The speed and resilience features

Parallel script running for the lint chain and local test chains; retry-once on exactly the four tests that talk to the live network (and nowhere else); the tiny static-file server that replaces a dev dependency (with its own contract test — the review caught that no existing suite actually covers it); and a flag that prevents orphaned dev-server processes. Each is its own commit, each independently revertable.

Proves itself by: full CI plus the packaged release-path test plus a live-testnet proving smoke, all green.

Phase 5 — the SDK cleanup (its own PR)

Remove the HTTP library from the published SDK

You asked for this one and the reviews agreed it's worth it — one fewer dependency that every SDK consumer installs. But they also proved it's surgery, not a swap: the library's error type silently drives the SDK's "is this a network failure or an HTTP failure?" decision, which in turn controls a security-relevant fallback. The replacement preserves that decision logic exactly — including the nasty edge where an error response's body can't be read (it must still count as an HTTP failure, never a network one) — with adversarial tests for precisely those edges, and zero change to the SDK's public API.

Proves itself by: the SDK's full test suites and live end-to-end runs green, with the error-classification tests intact and the public-API snapshot untouched.

What we deliberately are NOT doing

Test sharding, changed-file test selection, auto-fixing dependency tools (against this repo's human-reviewed-bumps philosophy), Bun's new browser automation (our Playwright suites are mature), its new parsers and terminal helpers (no such needs exist in this repo), and — cut on review advice — swapping the Windows archive-extraction path (the current code works, the new API can't yet enforce the same safety bounds, and the win was six lines). The wildcard version of our supply-chain exclusion list still doesn't work in 1.4 (tested), so the 31-name list stays.
