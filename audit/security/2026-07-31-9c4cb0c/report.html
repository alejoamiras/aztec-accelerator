Status update — 6 August 2026: six of these are fixed

Everything below describes the codebase as the audit found it on 31 July. Six findings have since been fixed on branch worktree-harden-security-bugs: F-01 (witness sent to an unauthenticated endpoint), F-02 (unvalidated CA installed into OS root stores), F-04 (one local write permanently disables updates), F-05 (trust removal reports failure as success), F-06 (unbounded cache growth), and the stderr half of F-08. Seven remain open: F-03, F-07, F-09, F-10, F-11, F-12, F-13.

Each fix carries regression tests that were mutation-proved — the fix was reverted and the test confirmed to fail — so the tests pin the defect rather than the current behaviour. The fixes then went through five rounds of independent adversarial review, which found thirteen further bugs, nine of them in the fixes themselves.

Update, 10 August: F-06's eviction race is now fully closed by an in-use lease (a further five review rounds). F-02's same-user file-replacement window remains open and is now known to be untestable on Windows — five separate routes to seed the certificate store without a consent dialog were measured and all failed, so closing it there would mean shipping security code CI can compile but never run. It stays an explicitly accepted risk rather than a claimed fix.

Full detail, including three places the fixes deliberately diverged from this report's own recommendations and why: report.md → “Remediation status (2026-08-06)”.

Verification changed some of this — read this first

Five findings were independently re-read from source before the verifier saw the claims. Nothing was refuted outright, but three were trimmed and two rationales were wrong:

  • F-03's version-floor claim is refuted. The launch floor commits the binary's own compiled-in version, not the value a spoofed responder reports, so a forged probe is a no-op there. The self-eviction half stands. Band drops 6.8 → ~5.0.
  • F-01's "not covered by any accepted residual" was wrong. The plaintext-by-default posture is a documented accepted decision. The finding still holds as High, but on the narrower ground that the authentication half of prior F-001's fix never shipped. Its host facet drops to Low — there is no environment-variable path to set it.
  • F-08's disclosure is asserted, not demonstrated. The certain harm is that the prover's diagnostics are lost entirely; the leak magnitude is unproven, and "accumulates over months" is unsupported.
  • F-02 and F-04 confirmed as written, including the claim the verifier tried hardest to break.

Nothing here has been fixed — no code changes have been made from this audit.

Cheapest fixes first

Three of these are hours of work and each removes a whole class of problem:

  1. F-05 — trust removal fails open. The correct tri-state already exists in trust/linux.rs:328-350; port it to macOS and Windows. Also bounds F-02's damage.
  2. F-04 (items 1–2) — permanent update lockout. Do this one first. Verification established this is not primarily an attack: a user who downgrades to an older build — the normal response to a bad release — is permanently and silently cut off from every future update, including the fix. Fall back to floor = current_running_version on corrupt or impossible state, and surface it in Settings. Costs nothing: candidate_allowed already enforces candidate > current before it ever consults the file (verified).
  3. F-08 (facet B) — dead stderr containment. One line restores a control that was written, tested, and has never actually run.

The two High findings

High 8.1F-01 verified: partial both modelsconfidence: high escalation of prior F-001 The SDK hands the private witness to an endpoint it never authenticates, in cleartext, by default

Your private transaction data is handed to whatever program answers a local port — in plaintext — because the app only asks it a question any program can answer correctly.

What it is. The SDK decides where to send your complete private transaction data by asking whatever program answers on a local port one question: “are you the accelerator?” It accepts a 31-byte JSON answer as proof. Any program on the machine can give that answer. The encrypted mode that would actually prove identity is off by default.

What an attacker would do. Run any unprivileged program that grabs port 59833 before the real app does, answer the one question correctly, and receive every private witness the user's dApps generate — then quietly forward each one to the real accelerator so proofs still succeed and nothing looks wrong. On a privacy chain, the witness is the plaintext of everything the chain exists to hide.

The fix. Default to the authenticated mode when it is available, and require an explicit opt-in for plaintext. Separately, build URLs with a real URL parser instead of string concatenation — today host: "127.0.0.1@attacker.tld" sends data to attacker.tld while the log still reads 127.0.0.1.

Technical trace

Trace. accelerator-prover.ts:126 (httpsOnly false) → accelerator-transport.ts:317-319 plaintext probe fired → :333-335 #isHealthy = response.ok && isRecognizedHealthBody(body) → :383-392 healthy HTTP wins when nothing is bound on :59834 → accelerator-prover.ts:222-226 protocol pinned http → :362 serializePrivateExecutionSteps → sink accelerator-transport.ts:455.

Why mitigations fail. The SDK's own comment concedes the identity check is “collision resistance, not authentication” (accelerator-transport.ts:44-50). redirect:"error" stops steering the witness after the endpoint is chosen, not choosing the wrong one. The generation guard is sound but prevents an unprobed endpoint, not a probed-but-unauthenticated one. The disclosed residual in the README describes the httpsOnly case, where the bar is forging browser trust; in the default mode the bar is binding a port. Corrected by verification: the plaintext-by-default posture IS a documented accepted decision (https-by-default-onboarding-2026-07-09/plan.md:18,131) — the earlier claim that it was covered by no residual was wrong. The finding stands on the narrower ground that prior F-001 asked for endpoint authentication and only the body-shape half shipped. The host facet drops to Low: there is no environment-variable ingress for it.

Prior audit. F-001's fix had two halves — authenticate the server, and stop trusting unrecognized bodies. Only the second shipped. This adds two sinks F-001 did not cover: the HTTPS→HTTP demotion re-probe, and the unvalidated host option.

Effort. Hours to a day for both steps; a per-install shared secret (the fix F-001 actually asked for) is days.

High 7.8F-02 verified: confirmed both modelsconfidence: high new The app installs whatever certificate is on disk into the OS root store, unvalidated and unscoped

The app installs whatever certificate is sitting in its folder into your operating system's trusted list: it checks the files match each other, not that they are its own.

What it is. Before installing its own certificate authority into your operating system's trust store, the app checks that the three certificate files on disk are consistent with each other — not that they are the ones it created. A check written to detect a half-finished file swap silently became the only thing standing between “our certificate” and “someone else's.”

What an attacker would do. Drop three files into ~/.aztec-accelerator/certs/ — a certificate authority they hold the private key for, plus a matching localhost certificate. When the user next runs first-time setup (the HTTPS toggle is pre-checked), the app installs the attacker's authority as a trusted root, and the operating system's approval prompt names Aztec Accelerator as the requester. The attacker can then impersonate any website to that user's browsers — and on macOS and Windows the trust is not limited to websites, so it also covers signed software.

The fix. Re-parse the certificate immediately before every trust-store write and require it to match the app's own profile: correct subject, CA flag, key usage, and the critical loopback name-constraint. Then scope the grant — -p ssl on macOS, an EKU restriction on Windows. Linux already scopes it correctly, which shows the narrower grant is achievable.

Technical trace

Trace. Attacker writes ca.pem, localhost.pem, localhost.key → commands.rs:566-577 complete_onboarding → :392 certs_exist() && is_ca_trusted() → certs.rs:145-152 certs_exist() returns true (files exist, leaf not expired, leaf matches key, leaf_matches_ca() passes) — it never inspects the CA's own basicConstraints, keyUsage, subject, or nameConstraints → certs.rs:228-234 generate_and_save() no-ops because the set already “exists” → :440-452 install_ca_trust() → trust/macos.rs:24-39 (add-trusted-cert, no -p policy) / trust/windows.rs:59-66 (-addstore Root, no EKU) / trust/linux.rs:283-300 (-t "C,,", correctly scoped).

Why mitigations fail. The keyless-CA design protects the anchor the app mints — a planted CA simply has a key. Name constraints exist only because ca_params() puts them there; a planted CA omits them and nothing checks. File permissions bound other users, not the same user — who this codebase already treats as in-scope. The OS consent dialog names the application, not the certificate's constraints.

Also affected. rotate() → trust_new_anchor() (certs.rs:412-434) has the same gap on staged files.

Effort. About a day — one validation function plus the two platform flags.

Medium findings

Med ~5.0F-03 verified: partial — band ↓ both modelsescalation of prior F-002 A forgeable /health shape is treated as proof of process identity

The app asks itself that same weak question, so an impostor holding the port can make the real app quietly shut down and can poison its rollback protection.

What it is. The same weak “are you the accelerator?” check from F-01 is used by the app on itself. If another program is already on the port, the real app assumes that program is a legitimate copy of itself.

What an attacker would do. Squat the port; on Windows the genuine app then exits with a success code deliberately chosen so its supervisor will not restart it — no tray icon, no error. The impostor keeps the port and keeps receiving witnesses. Correction from verification: an earlier draft of this finding also claimed the impostor could poison the anti-rollback version floor. That is wrong — the floor commits the running binary's own compiled-in version, not the probed value, so a forged probe is a no-op there.

The fix. Use an OS single-instance primitive (named mutex, abstract socket, lock file) for the “am I redundant?” decision instead of an HTTP probe, and never advance the version floor from a self-declared value.

Technical trace

probe.rs:14-17 is the entire identity test (two constant fields, both part of the public contract). Sink A: probe.rs:24-45 → main.rs:294-303 app_handle.exit(0) — the comment at :290-292 confirms the exit code is chosen so restart-on-failure will not retry. Sink B: probe.rs:54-71 → main.rs:347-355 commit_launch_floor(). Sink C: probe.rs:41,64 parse the response with no size cap. Bind side: bind.rs:30 sets no SO_EXCLUSIVEADDRUSE on Windows.

Prior audit. Escalation of F-002 (Medium). The prior fix was never applied, and F-004's own remediation (commit_launch_floor) was then built on top of the unfixed probe.

Effort. Sinks B and C are hours; sink A is 1–2 days (platform-specific).

Med 6.5F-04 verified: confirmed both modelsnew A one-shot local write permanently disables the update channel — and survives reinstall

Writing about 40 bytes into a file in your home folder switches off every future security update, permanently — and reinstalling does not clear it.

What it is. Two files in the user's home directory — the updater's version floor and the Windows update marker — are trusted without any authenticity check. Anything running as the user can write them once and permanently switch off updates, crash recovery, and the autostart self-repair.

What an attacker would do. Write about 40 bytes: {"schema":1,"floor":"999.0.0"}. That is a perfectly valid file, so nothing rejects it, and the value only ever moves upward, so nothing undoes it. Every future security fix is refused, silently. Uninstalling and reinstalling does not help — the uninstaller only removes the certificate folder. A user who simply downgrades to an older build trips the same trap by accident.

The fix. On corrupt or impossible state, fall back to floor = current_running_version rather than refusing forever. The anti-rollback property is preserved regardless, because the candidate-must-exceed-current check does not depend on the file at all.

Technical trace

Variant A (valid poison): updater_state.rs:75-99 parses cleanly → updater.rs:136-142 layer_b_gate → updater_state.rs:140-142 running_below_floor → refuse. Irreversible because :162-173 and :189-198 are monotonic-max. Variant B (corrupt): every mint at :76-98 → :122-123 rejects all candidates; both mutators (:154-159, :183-187) refuse to repair. Variant C (lock denial): updater.rs:51-57 .ok()? silently conflates “another instance holds it” with “unopenable”, disabling installs, floor commits, and — as collateral — the autostart heal (autostart.rs:1365-1367). Windows marker equivalent: update_marker.rs:141-168 validates shape only; a forged 24-hour deadline suppresses heal, rearm and updates, and the disarm at updater.rs:443 is not rolled back.

Persistence. nsis/hooks.nsi:88-113 removes only certs/; macOS and Linux have no uninstall hook at all.

Effort. Items 1–2 are hours and remove the permanent lockout; authenticating the marker is 1–2 days.

Med 6.1F-05 both modelsfix: hours · CHEAPEST Trust removal fails open on macOS and Windows — failure is reported as success

When you revoke the app's certificate authority, “we could not check” is reported back to you as “removed”, so it can stay trusted forever.

What it is. When the user revokes the app's certificate authority, the code treats “I could not ask the operating system” as “it is gone.” Settings says removed; the uninstall command exits successfully; the trusted root is still installed.

What an attacker would do. Mostly nothing — this fires on its own. A blocked certutil.exe (commonly restricted by endpoint security), a locked macOS keychain, or running the uninstall under a different HOME all produce a false success. An attacker who planted a certificate under F-02 only needs to make the removal fail to keep it trusted forever.

The fix. Linux already solved this with a three-state result — present / absent / could not determine — where “could not determine” counts as still trusted and fails loudly. Port those ~20 lines to the other two platforms, and make the Windows uninstaller call the verified command instead of a bare unchecked one.

Technical trace

macOS: trust/macos.rs:61-71 keychain_sha1() swallows spawn failure into None and never inspects output.status → the delete loop breaks before attempting any deletion (:126-136) → :140 reports not-present → StoreStatus{installed:false}. Windows: trust/windows.rs:125-130 discards the delete result entirely; :70-76 unwrap_or(false) makes a spawn failure read as “absent”. Sinks: trust/mod.rs:88-100 removal_incomplete() false → Settings success and main.rs:486-507 exit code 0. Reference implementation: trust/linux.rs:328-350 (Present::{Yes,No,Unknown}) and :497. Amplifier: nsis/hooks.nsi:109 runs a bare certutil -delstore with no exit-code check on the one path where removal matters most.

Med 6.3F-06 both modelsnew An HTTP header chooses which native binary gets downloaded and executed, and how much disk is consumed

A website can name any old version of the prover in a request header, and the app will download it, install it, and run it on your private data.

What it is. Any approved website can name a version in a request header, and the app will fetch that version of the prover binary from GitHub, install it, and run it against the private witness. There is no floor, no allowlist of tested versions, and the revocation list is an empty compile-time constant — so revoking a bad version requires shipping a whole new app release.

What an attacker would do. Two things. Pick an old release with a memory-safety bug and feed it crafted input, since the same origin controls both the binary choice and the bytes it processes. Or simply enumerate hundreds of historical releases with a 2-byte request body each — the download completes before the body is ever examined — filling the disk with tens of gigabytes that are never evicted, because unrecognized prerelease labels fall into a keep-forever tier.

The fix. Bound the accepted range to versions this build was tested against, cap the cache by total size, and make the retention policy fail closed for unknown tiers rather than keeping forever.

Technical trace

Selection: prove.rs:249-253 header → version_policy.rs:240-260, whose only semantic gate is an empty KNOWN_VULNERABLE_VERSIONS (:194) → release_metadata.rs:54-60 builds the URL from the attacker's string → downloader.rs:55 installs (on macOS the app re-signs it, :83-86) → bb.rs:206,229 executes. Retention: version_policy.rs:52 Mainnet limit is None; :30-44 routes any unrecognized prerelease into Mainnet; :299 exempts anything under 5 minutes old; and the only eviction call site is the post-download tokio::spawn at prove.rs:287-299. A third facet: each version-bearing request hashes the whole 37 MB binary twice synchronously on the async runtime (prove.rs:108, bb.rs:38).

Not the same as SEC-02 (the accepted “digest comes from the same control plane” gap) — this holds even with a perfect digest chain, because the attacker selects an authentic binary.

Med 6.0F-08 verified: partial claudefix: hours · CHEAPEST Witness data escapes the controls designed to contain it

Private witness files are deleted only by a cleanup step the app's own Quit button skips, and the redaction code for the prover's error output has never once run.

What it is. Two containment controls do not do what they appear to. The private witness file is deleted only by a destructor that the app's own Quit and auto-update restart paths skip — so quitting mid-proof leaves the plaintext on disk permanently, with nothing to clean it up later. And the prover's error output was supposed to be truncated and kept server-side, but the child process inherits the app's output streams, so the captured buffer is always empty and that code has never executed.

What an attacker would do. Nothing active — residue accumulates on its own, and whoever later gets same-user access, the laptop, or the backup can read it. Verification note: the volume ("months of witnesses") is unsupported, and for the stderr half the demonstrated harm is that the prover's diagnostics are lost entirely rather than a proven leak.

The fix. Sweep the workspace directory at startup (the version cache already has exactly this), and either pipe the child's stderr so the existing truncation runs, or discard it explicitly.

Technical trace

Facet A: bb.rs:194-198 writes the witness into a TempDir whose Drop is the only deletion; skipped by main.rs:301,396, updater.rs:542, commands.rs:666, and the Windows NSIS handoff. No startup reaper exists anywhere (repo-wide grep). Facet B: bb.rs:206-229 configures no stdio, so std::process::Command defaults to inherit; wait_with_output() therefore returns an empty stderr and the guard at :238-241 is unreachable, leaving truncate_stderr (:272-280) dead. The 0700 log dir and its rotation never see the data. Verified against tokio's shipped source.

Med 5.9F-09 codex onlycross-model disagreement The updater accepts a byte-for-byte replay of a withdrawn but validly signed release

A withdrawn-but-still-signed release can be replayed at users, because a signature proves a release is genuine, not that it is current.

What it is. If a release is published and then withdrawn — because it was broken or malicious — anyone who can serve the update feed can replay that exact signed manifest, and it still verifies. Signatures prove authenticity, not currency.

What an attacker would do. Requires control of the update feed, so this is gated behind a separate compromise. Given that, they can pin every user to a specific withdrawn version rather than the current one.

The fix. Persist the highest version and newest publication date ever seen, and refuse anything at or below both. Note this was found by only one of the two model families — the Claude leg explicitly verified the envelope binding as complete and did not flag replay, which is exactly the kind of divergence worth recording.

Technical trace

Layer A binds every consumed field to the signature, and the plugin plus candidate_allowed both enforce candidate > current — so a downgrade is blocked. What is not blocked is a lateral replay of a higher, withdrawn, validly signed release. Escalation of prior F-004's residual. Real-world severity is gated on prior F-005 (deploy trust reaching the update feed), which lives in the out-of-scope infrastructure and was not re-verified here.

Med 5.6F-10 both modelsconfidence: moderate Consent windows accept clicks before the anti-click-steal guard applies

A second approval popup can appear under your cursor in the same spot and accept the reflexive re-click — permanently approving a site you never saw.

What it is. The approval popup ignores clicks for 700 ms after it gains focus, so a window appearing under the user's cursor cannot capture a click. But when a queued popup is promoted, the buttons are enabled by a once-per-second poll — so the guard can be fully expired at the moment the buttons become clickable. Separately, three other windows that appear unprompted and take focus (onboarding, certificate renewal, update prompt) do not use the guard at all.

What an attacker would do. Open two approval prompts from two origins at once. The second sits invisibly beneath the first at identical coordinates. The user clicks Allow on the one they expected; it closes; the second appears in the same pixels. The reflexive “it didn't register” re-click can land on an origin the user never saw — and approval here is permanent.

The fix. Re-arm the guard on the moment buttons become enabled, not on focus. Apply the guard to the other three consent windows — on Linux the onboarding “Start” click installs a browser-trusted CA with no OS prompt at all.

Technical trace

Guard armed on focus (bridge.js:30,34-37,40-42); buttons enabled by a 1000 ms poll (authorize.js:81-87, :68); promotion at commands.rs:226-233. Worst case is deterministic rather than racy: if the user had already clicked the queued window, it already holds focus, so set_focus() fires no focus event and the promoted popup goes live with no guard at all. No test covers this — the Playwright mock sets the guard to 0 ms (e2e/tauri-mock.js:14) and the WebDriver spec sleeps past it. Unguarded consent controls: onboarding.js:86, renewal.js:5-11, update-prompt.js:8-15, against the invariant asserted at bridge.js:38-39.

Med 5.9F-07 both models Authorization-prompt flooding starves every legitimate site of the consent path

Ten iframes from one attacker page fill every approval slot, so your real dApp is refused outright and never even shows you a prompt.

What it is. Ten pending approval slots, shared globally, first-come-first-served, with no grouping by site and no memory of denials.

What an attacker would do. One page with ten sub-domain iframes fills all ten slots. The user's real dApp is refused outright and appears broken, with no prompt ever shown. Each attacker popup auto-denies after 60 seconds and is immediately re-requested — nothing remembers the denial — so the queue never drains and the user faces an endless stream of near-identical dialogs.

The fix. Group the cap by registrable domain, remember denials with a backoff, and reserve at least one slot for an origin not seen before.

Technical trace

authorization.rs:344-346 is the only global limiter (10 slots, un-grouped); auth.rs:118-121 returns OriginDenied and records nothing. MAX_PIGGYBACK_SENDERS bounds fan-out within one origin only. The single-active-popup arbiter reduces click-hijacking but lengthens the drain to ~60 s per queued origin, strengthening the availability impact. MAX_INFLIGHT_PROVE does not apply — authorization runs before it.

Med 5.4F-12 claudedocumented risk decision AppImage provenance uses a containment test, so any ancestor passes as $APPDIR

The check for “is this really my AppImage?” accepts any parent folder, so two environment variables let an attacker choose what the app pins as startup persistence.

What it is. On Linux the app trusts two environment variables to learn where its own AppImage lives, guarding against inherited values by checking that its executable sits somewhere under the claimed directory. Setting that directory to / satisfies the check for any absolute path.

What an attacker would do. Set two environment variables in the user's session and drop a payload. The app then writes that payload's path into the autostart entry and the systemd recovery unit — persistence that rewrites itself on every launch and is attributed to a legitimately signed application.

Important context. This is not an unnoticed bug. When the containment check was added earlier the same day, APPDIR=/ was explicitly considered and the risk accepted on the grounds that spoofing it already implies control of the app's launch environment. That was a reasonable call under a correctness lens; it is worth re-taking under a security lens, because the payoff here is durable persistence rather than a one-time action.

Technical trace

autostart.rs:1197 exe_c.starts_with(&dir_c) is the whole provenance test. Consumers: :1227-1229 (.desktop Exec=), crash_recovery.rs:264 (systemd ExecStart=, reads the env independently), and autostart.rs:1627-1632, where the poisoned path is passed as the ownership reference — inverting the very anti-theft gate added alongside it. Suggested fix: compare the device ID of current_exe() against /, or require $APPDIR to be a real mountpoint per /proc/self/mountinfo. Effort: hours including the test.

Med 5.3F-11 both models The SDK reads the prove response with no size cap, deadline, or abort path

The app carefully bounds the small health response but not the large proof response, so a hostile responder can hang or crash the browser tab.

What it is. The health check in the same file is carefully bounded — 64 KB cap, 2-second deadline, stall detection. The much larger prove response, from the same untrusted responder, has none of that. The HTTP client's timeout stops counting once headers arrive.

What an attacker would do. Answer the prove request with headers and then either nothing or an endless stream. The dApp's promise never settles or its tab runs out of memory — and the UI has already been told the proof succeeded, because that message fires before the body is read.

The fix. Reuse readJsonBounded, which already exists in the same file, and accept a caller-supplied abort signal.

Technical trace

Sink accelerator-prover.ts:508. ky clears its timeout timer when fetch() resolves at headers (utils/timeout.js); its 10 MB error-body cap is only applied on the non-2xx path (Ky.js:143), so a 200 never touches it. The hardened counterpart is accelerator-transport.ts:63-143, added deliberately for exactly this threat on /health. The asymmetry is the evidence it is an oversight, not an accepted residual.

Low 3.8F-13 claudefix: <1 hour schtasks.exe is located through an environment variable its sibling deliberately distrusts

One Windows helper is located through an environment variable that the code directly next door deliberately distrusts — the fix is copying four lines.

What it is. The Windows crash-recovery code finds schtasks.exe via %SystemRoot%. The trust-store code next door resolves the same class of tool by preferring the hardcoded C:\Windows\System32 path first, and its comment explains exactly why. The hardening was applied to one and not the other.

What an attacker would do. Point %SystemRoot% somewhere else. Omit the binary and every update is silently refused; supply a stub that lies about the task's state and the updater proceeds to rewrite files while the every-minute relaunch task is still armed.

The fix. Copy the four lines from trust/windows.rs:36-47.

Cross-cutting observations

Hardening applied on the write path but not the read path

The update marker is created with owner-only Windows ACLs, but the code that reads a marker never checks the owner or ACL of one it did not create. The certificate set is written with 0600 permissions and atomic renames, but the code that installs it never re-validates what it is installing. In both cases the protective work went into producing the file, and the consuming path trusts whatever it finds.

A control exists on one platform and not its siblings

Linux has the tri-state trust-removal result; macOS and Windows do not (F-05). Linux scopes the certificate trust grant; macOS and Windows do not (F-02). trust/windows.rs distrusts %SystemRoot%; crash_recovery.rs does not (F-13) — and the former's comment even cites the latter as the pattern it follows. Each of these is a fix that was reasoned through once and applied incompletely.

Documentation asserts invariants the code does not enforce

bridge.js:38-39 states that every consequential control is guarded; three of four are not. cache_layout.rs:208 calls the integrity marker “the single authority the runtime trusts”, which overstates what an unauthenticated JSON file can be. probe.rs:11-13 claims its check prevents an arbitrary process from being accepted; it checks two public constants. These comments are load-bearing for reviewers, and each one currently misleads.

Yesterday's fixes are today's findings

Two remediations from the previous audit became findings here: the launch-floor commit (F-004's fix) is gated on the forgeable probe from F-002, whose own fix was never applied; and the updater state file it introduced is a one-line permanent-lockout primitive. This is the strongest argument for auditing remediation code specifically, rather than treating a closed finding as closed ground.

Coverage gaps — what this audit did not examine

  • Out of scope by request: the headless server crate, the playground and landing packages, all CI/CD workflows, and the Terraform infrastructure. F-09's real-world severity depends on prior F-005, which lives in that infrastructure and was not re-verified.
  • One missing cross-model leg. The Codex agent for the persistence cluster did not finish in time to be folded into the reduce stage, so F-12 and F-13 have no second-family corroboration — in exactly the cluster flagged as a priority concern.
  • One unresolved uncertainty flag. snapshot_restore_roundtrip_for_tests is a public function in the production library that mutates real autostart state; no caller was found, and no agent examined whether it is reachable in a shipped build.
  • Depth. This ran at medium effort: two independent agents per cluster with no cross-rebuttal round, and verification limited to five findings by severity bucket.
