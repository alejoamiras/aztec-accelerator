Two findings meet the reporting bar.

## Finding 1 — Incomplete F-001 remediation: a forgeable `/health` marker still authorizes witness delivery to an impostor

1. **Title.** The prior F-001 server-impersonation fix is incomplete: `{}` is now rejected, but the public static health marker still causes private witnesses to be sent over the default HTTP fallback.

2. **Impact factors.**

   - **Confidentiality:** violated. The serialized `PrivateExecutionStep[]` contains the private transaction witness.
   - **Authorization/authenticity:** violated. An unauthenticated local process is treated as the authorized accelerator.
   - **Blast radius:** every proof generated by the victim dApp while the attacker controls the configured port; applicable across SDK consumers using the default non-strict configuration.
   - **Data sensitivity:** maximal for this application—a privacy-chain transaction witness.
   - **Attack vector:** local process controlling `127.0.0.1:59833`.
   - **Complexity:** low once the port is available.
   - **Privileges:** no elevation is required to bind this unprivileged loopback port.
   - **User interaction:** only normal use of a dApp that requests a proof.

3. **Evidence confidence.** **High.** The complete health-response-to-witness-POST path is explicit. This is specifically an **incomplete fix of prior F-001**, not a new framing of the accepted absent-`Origin` behavior.

4. **OWASP / CWE mapping.** [OWASP A07:2025 Authentication Failures](https://owasp.org/Top10/2025/A07_2025-Authentication_Failures/); CWE-306, Missing Authentication for Critical Function, currently #21 in the [2025 CWE Top 25](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html). Secondary: CWE-940, Improper Verification of Source of a Communication Channel.

5. **Trace.**

   1. Strict HTTPS is disabled by default at [`accelerator-prover.ts:126`](/home/homelab/Projects/aztec-accelerator/aztec-accelerator-1/.claude/worktrees/harden-security-bugs/packages/sdk/src/lib/accelerator-prover.ts:126), and the default host/ports are passed into the transport at `accelerator-prover.ts:128-133`.
   2. The SDK probes HTTPS but also constructs and fires the plaintext HTTP probe at [`accelerator-transport.ts:302`](/home/homelab/Projects/aztec-accelerator/aztec-accelerator-1/.claude/worktrees/harden-security-bugs/packages/sdk/src/lib/accelerator-transport.ts:302) and `accelerator-transport.ts:315-320`.
   3. The attacker-controlled `Response` and parsed body enter at `accelerator-transport.ts:304-313`.
   4. The only identity-like check is `status === "ok" && api_version === 1` at `accelerator-transport.ts:52-56`; it is applied at `accelerator-transport.ts:333-335`.
   5. With HTTPS unavailable, a matching HTTP response wins at `accelerator-transport.ts:383-391`.
   6. The prover receives the response at [`accelerator-prover.ts:196`](/home/homelab/Projects/aztec-accelerator/aztec-accelerator-1/.claude/worktrees/harden-security-bugs/packages/sdk/src/lib/accelerator-prover.ts:196), repeats the same public-shape check at `accelerator-prover.ts:211`, and casts the optional version fields at `accelerator-prover.ts:218`.
   7. With both optional version fields omitted, the classifier skips `available_versions` at `accelerator-prover.ts:250-267`, does not enter the mismatch branch at `accelerator-prover.ts:269-287`, and returns `available: true` at `accelerator-prover.ts:289`.
   8. The attacker’s protocol is pinned at `accelerator-prover.ts:222-225`.
   9. `createChonkProof` accepts that status at `accelerator-prover.ts:310-329`, snapshots the pinned URL at `accelerator-prover.ts:351`, and serializes the private execution steps at `accelerator-prover.ts:361-362`.
   10. The bytes are handed to `postProve` at `accelerator-prover.ts:381`.
   11. **Sink:** `ky.post` sends those bytes as the request body to the impostor at [`accelerator-transport.ts:450`](/home/homelab/Projects/aztec-accelerator/aztec-accelerator-1/.claude/worktrees/harden-security-bugs/packages/sdk/src/lib/accelerator-transport.ts:450), specifically `accelerator-transport.ts:455-466`.

6. **Missing control.** There is no cryptographic or unpredictable proof of server identity before witness transmission: no mandatory authenticated TLS policy, per-install challenge/token, pinned identity, or equivalent OS-authenticated channel. Two public constants are treated as sufficient identity.

7. **Exploit story.**

   1. The genuine accelerator is absent, stopped, or loses the startup race.
   2. An unprivileged process binds `127.0.0.1:59833`, enables CORS for the victim origin, and handles the `/prove` preflight.
   3. It responds to `/health` with:
      ```json
      {"status":"ok","api_version":1}
      ```
   4. The HTTPS probe fails, while the attacker’s HTTP response passes the static shape check and is pinned.
   5. The user initiates a private transaction in an SDK-using dApp.
   6. The SDK POSTs the complete serialized witness to the attacker’s `/prove`, which records it. Any later fallback or malformed response occurs after disclosure.

8. **Preconditions.**

   - The attacker can run local code and control the configured HTTP port before the genuine accelerator.
   - `httpsOnly` remains false, as it is by default.
   - The browser permits loopback HTTP and the victim dApp requests accelerated proving.
   - The impostor returns suitable CORS headers.

9. **Why mitigations fail.**

   - The previous bare-JSON bypass was narrowed, but the replacement marker is static and public; it provides collision resistance, not authentication, as acknowledged at `accelerator-transport.ts:44-50`.
   - HTTPS is preferred, not mandatory. `accelerator-transport.ts:317-319` still probes HTTP and `accelerator-transport.ts:253-258` uses it when selected.
   - The installed CA protects a genuine HTTPS connection but does not protect the permitted HTTP fallback.
   - Host guards and Origin authorization are implemented by the genuine accelerator. An impostor simply does not enforce them.
   - Redirect blocking and configuration-generation guards prevent endpoint steering and races; they do not establish endpoint identity.
   - `httpsOnly` would close this HTTP path, but it is opt-in rather than the default.

10. **Instances.**

   - Initial dual-probe selection: `packages/sdk/src/lib/accelerator-transport.ts:302-319,333-335,383-391`.
   - HTTPS-demotion revalidation uses the same forgeable marker: `packages/sdk/src/lib/accelerator-transport.ts:415-430` → `packages/sdk/src/lib/accelerator-prover.ts:423-447`.
   - Shared classification and pin: `packages/sdk/src/lib/accelerator-prover.ts:196-225,242-289`.
   - Witness serialization and transmission: `packages/sdk/src/lib/accelerator-prover.ts:351-381` → `packages/sdk/src/lib/accelerator-transport.ts:450-466`.
   - Default non-strict policy: `packages/sdk/src/lib/accelerator-prover.ts:126-133`; `packages/sdk/src/lib/types.ts:32-37`.

## Finding 2 — Unbounded `/prove` response parsing lets a controlled endpoint exhaust browser memory

1. **Title.** An attacker-controlled successful `/prove` response is fully buffered, JSON-parsed, and base64-decoded without a byte limit.

2. **Impact factors.**

   - **Availability:** violated. A response can freeze or terminate the dApp’s renderer/browser process through memory exhaustion.
   - **Blast radius:** at least the victim dApp renderer; shared renderer processes or system-wide memory pressure may affect other tabs and applications.
   - **Data sensitivity:** no additional secret is required; the affected asset is the ability to complete private transaction proving.
   - **Attack vector:** a malicious local listener selected through Finding 1, or another attacker-controlled configured accelerator endpoint.
   - **Complexity:** low; the response can be ordinary valid JSON containing a very large string.
   - **Privileges:** local code execution sufficient to control the loopback port; no elevation.
   - **User interaction:** a normal proof request.
   - **Repeatability:** every proof request can trigger another allocation attempt.

3. **Evidence confidence.** **High.** The success body goes directly through `Response.json()` and `Buffer.from` with no length check or bounded reader.

4. **OWASP / CWE mapping.** [OWASP X01:2025 Lack of Application Resilience](https://owasp.org/Top10/2025/X01_2025-Next_Steps/) (on-the-cusp category); CWE-770, Allocation of Resources Without Limits or Throttling, currently #25 in the [2025 CWE Top 25](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html). Secondary: CWE-400, Uncontrolled Resource Consumption.

5. **Trace.**

   1. An untrusted `/prove` response enters through `ky.post` at [`accelerator-transport.ts:455`](/home/homelab/Projects/aztec-accelerator/aztec-accelerator-1/.claude/worktrees/harden-security-bugs/packages/sdk/src/lib/accelerator-transport.ts:455).
   2. The primary path assigns it to `res` at [`accelerator-prover.ts:381`](/home/homelab/Projects/aztec-accelerator/aztec-accelerator-1/.claude/worktrees/harden-security-bugs/packages/sdk/src/lib/accelerator-prover.ts:381); the downgrade-retry path does the same at `accelerator-prover.ts:443-447`.
   3. The primary response is passed to `#decodeProof` at `accelerator-prover.ts:483-484`; the retry passes it at `accelerator-prover.ts:448`.
   4. **First sink:** `await res.json()` consumes and parses the entire attacker-controlled body at `accelerator-prover.ts:508`.
   5. **Second sink:** the attacker-controlled `proof` string is decoded into another allocation with `Buffer.from(..., "base64")` at `accelerator-prover.ts:510`.
   6. The resulting buffer is then handed across the parser boundary at `accelerator-prover.ts:511`.

6. **Missing control.** The proof response lacks a protocol-derived maximum size, incremental byte-counted reader, `Content-Length` precheck, hard body deadline, and pre-allocation validation of the JSON shape/base64 length.

7. **Exploit story.**

   1. The attacker becomes the selected accelerator endpoint and returns a valid health marker.
   2. After receiving a witness at `/prove`, it immediately returns `200 OK`.
   3. The body is valid JSON such as `{"proof":"AAAA…AAAA"}`, with hundreds of megabytes of `A` characters; chunked encoding can omit a declared size.
   4. `res.json()` retains and parses the entire body.
   5. `Buffer.from` then creates a second large decoded allocation before the proof parser can reject it.
   6. The renderer freezes, is killed for out-of-memory, or imposes significant memory pressure. The attacker repeats this for later transactions.

8. **Preconditions.**

   - The attacker controls an endpoint that the SDK uses for `/prove`.
   - The endpoint returns a readable CORS-enabled `200` response.
   - The victim requests a proof.
   - The response is sufficiently large relative to available renderer memory.

9. **Why mitigations fail.**

   - The SDK already has a 64 KiB bounded streaming reader at `accelerator-transport.ts:25-26,63-143`, but it is used only for `/health` at `accelerator-transport.ts:313,430`.
   - The ten-minute request timeout at `accelerator-transport.ts:28,457` limits time, not total response bytes; a large finite response can arrive quickly over loopback.
   - The catch at `accelerator-prover.ts:483-493` runs only after the full-body parse/allocation attempt. It cannot recover if the renderer is terminated and does not prevent peak memory consumption.
   - `ChonkProofWithPublicInputs.fromBuffer` is invoked only after the unbounded JSON and base64 allocations, so parser rejection is too late.
   - The genuine server’s normal proof size is not a control against an impersonating or compromised endpoint.

10. **Instances.**

   - Shared unbounded decoder: `packages/sdk/src/lib/accelerator-prover.ts:501-511`.
   - Primary response path: `packages/sdk/src/lib/accelerator-prover.ts:381,483-493`.
   - HTTPS-to-HTTP retry response path: `packages/sdk/src/lib/accelerator-prover.ts:443-448`.
   - Network handoff supplying both paths: `packages/sdk/src/lib/accelerator-transport.ts:450-466`.
